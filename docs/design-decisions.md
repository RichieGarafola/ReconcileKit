# Design decisions

## Integer cents instead of floating-point money

Binary floating point cannot represent most decimal fractions exactly (`0.1 + 0.2 != 0.3`).
In reconciliation, a one-cent drift turns an exact match into a false exception, or hides a
real one. ReconcileKit therefore:

- reads every value as text, so type inference never touches an amount;
- checks the text strictly (plain digits, at most two decimals, no exponent, sign,
  separators, or currency symbol) before calling `Decimal`;
- converts to integer cents straight away, and does all sums, comparisons, and storage
  (DuckDB `BIGINT`) in integers;
- formats money for display and export from those integers (`format_cents`), never through
  a float.

It never rounds. `99.999` is rejected rather than turned into `100.00`, because a silent
correction would make the output disagree with the source system without anyone noticing.

## Exact references instead of fuzzy matching

A payment is applied only when its trimmed `customer_id` and `invoice_id` equal one valid
invoice's identity. Fuzzy matching, and matching on amount or date, can look confident and
still be wrong. Two invoices for the same amount, or one customer paying two invoices on
the same day, are routine. A wrong automatic allocation is worse than an honest "unmatched",
because it understates what is owed and looks resolved.

Normalization is limited to removing surrounding whitespace. Whitespace is almost always an
export artifact, and every use of it is disclosed in the explanation. Case, punctuation,
and leading zeros often carry meaning (`000123` ≠ `123`), so they are preserved. When a
reference differs from a real invoice only by case or punctuation, the explanation says so
as a hint for the reviewer, and the payment still does **not** match.

## Quarantining whole duplicate identity groups

If an invoice identity appears twice, there is no principled way to choose a row. "Take the
first" depends on export order, and "take the larger" is a guess. ReconcileKit quarantines
every row in the group and marks any payment that references it AMBIGUOUS.

Duplicate groups are detected **before** rows with other problems are filtered out.
Otherwise a duplicate with a malformed amount would be dropped first, and its sibling would
look unique and be matched with confidence. Rows are compared after the same normalization
used for matching, so `" INV-1 "` and `"INV-1"` are duplicates.

## Immutable findings plus append-only reviews

The automated result records what the rules concluded from specific input bytes. Letting
a reviewer edit it would erase the evidence of what the data said. A review is therefore a
separate event row (who, which disposition, note, UTC time, unique id), and the current
disposition is derived from the latest event. Reviews never change allocations, amounts,
totals, or the completeness flag. To fix the data, the user corrects the source files and
re-imports them, which creates a new run with its own fingerprint.

Review event IDs are generated by the client and inserted idempotently, so a Streamlit rerun
or a double click cannot record the same decision twice.

## Local DuckDB storage

DuckDB is a single embedded file with real SQL, transactions, and constraints, and no
server, credentials, or network exposure, which suits a local single-user tool. Each run is
written in one transaction. The run ID derives from a fingerprint of the input file hashes,
rule configuration, as-of date, and engine/rule versions, so byte-identical re-imports reuse
the stored run. The trade-off is that DuckDB allows only one writer process at a time. That
is fine here and would need revisiting for a shared, multi-user service.

## Why AI is outside v1

The point of the tool is to explain each outcome with a stable rule code and evidence that
can be traced back to the source. A model-generated match or summary is not reproducible
from the same inputs, cannot easily be audited, and could state money facts that the
arithmetic does not support. Deterministic rules come first. Any later AI help, such as
drafting a reviewer note, would have to sit outside the findings and never change them.
